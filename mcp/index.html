    SuperQuantX MCP Server for AI Assistants¶

    SuperQuantX ships a Model Context Protocol (MCP) server so that AI assistants such as Claude Desktop, Cursor, or any MCP client can build and run quantum circuits, compare backends, and run small quantum machine learning and optimization experiments through one unified API.

    The server speaks MCP over stdio, uses the official mcp Python SDK (2.x), and runs on simulators only by default.

    Install¶

    Run the server with no install step (uvx fetches the pinned release into an isolated environment):

    uvx --from "superquantx[mcp]==0.3.0" superquantx-mcp

    Or add it to a uv project, with optional Qiskit and PennyLane backends:

    uv add "superquantx[mcp,qiskit,pennylane]==0.3.0"
uv run superquantx-mcp
# or, from a checkout
uv pip install ".[mcp,qiskit,pennylane]"
# or with pip
pip install "superquantx[mcp,qiskit,pennylane]==0.3.0"

    The mcp extra needs Python 3.10 or newer (SuperQuantX itself requires 3.11+). The built-in simulator backend works with no extra SDK, so uv add "superquantx[mcp]==0.3.0" is enough to try it.

    Two equivalent entry points start the server on stdio:

    superquantx-mcp
python -m superquantx.mcp

    Both are meant to be launched by an MCP client, not used interactively. superquantx-mcp --help prints the supported environment variables.

    Tools¶

    Tool What it does
    list_backends Every SuperQuantX backend with SDK install status, initialization, and a 2 qubit Bell smoke test. Status is working, not_installed, init_failed, execution_failed, or wrong_results.
    backend_versions Installed versions of SuperQuantX, Python, numpy/scipy/scikit-learn, every quantum SDK, and per-backend version info.
    run_circuit Run a circuit given as OpenQASM 2, OpenQASM 3, or a JSON gate list. Returns counts, probabilities, gate counts, and timing (parse, backend init, execute, total).
    bell_state_demo Run the same Bell circuit on several backends and report how many shots are correlated (00 or 11).
    qsvm_classify Quantum kernel SVM (SuperQuantX QuantumSVM) on a toy dataset or your own data, with kernel diagnostics and an RBF SVM baseline on the same split.
    qaoa_maxcut QAOA for MaxCut on a small graph with a classical optimizer, checked against exact brute force.

    Every tool returns structured JSON with "ok": true or "ok": false plus an error object. Tools never raise: bad input comes back as ValidationError, and a backend failure is reported for that backend only (for example bell_state_demo still returns results for the backends that work).

    Circuit input formats¶

    OpenQASM 2:

    OPENQASM 2.0;
include "qelib1.inc";
qreg q[2];
creg c[2];
h q[0];
cx q[0],q[1];
measure q -> c;

    OpenQASM 3 (qubit[n] / bit[n] declarations, c = measure q;) is accepted too. The parser supports a safe subset: standard gates (id x y z h s sdg t tdg sx rx ry rz p u1 u2 u3 u cx cz swap ccx and common aliases such as cnot, toffoli, phase), register broadcast (h q;), parameter expressions with pi and basic math (rz(-3*pi/4) q[0];). Gate definitions, classical control flow, and reset are rejected with a clear message. measure and barrier are accepted and ignored, since every qubit is measured at the end.

    JSON gate list (a list, or an object with n_qubits and gates):

    {"n_qubits": 2, "gates": [
  {"gate": "ry", "qubits": [0], "params": ["pi/3"]},
  {"gate": "cx", "qubits": [0, 1]}
]}

    Parameters may be numbers or expression strings such as "pi/3", evaluated without eval.

    Bit order. Counts are little-endian, the Qiskit convention: qubit 0 is the rightmost bit. All backends are normalized to this order (PennyLane results are reversed internally).

    Notes on qsvm_classify¶

    • Datasets: moons, circles, blobs, xor (2 features) and iris (versicolor vs virginica, 4 features). Or pass X, y (and optionally X_test, y_test).
    • kernel="statevector" (default) computes the exact fidelity kernel |<phi(a)|phi(b)>|^2 from the statevectors of a Qiskit-convention ZZFeatureMap (or ZFeatureMap) produced by the selected backend SDK, then trains SuperQuantX QuantumSVM with it. Simulator, Qiskit, and PennyLane give identical kernels for the same data.
    • kernel="backend" uses the backend's own compute_kernel_matrix. Since 0.3.0 this is a fidelity kernel built from real quantum states. The tool reports kernel_diagnostics.looks_valid and warns if the diagonal deviates from one or a backend reports a fallback.
    • bandwidth (default 0.5) scales features before encoding. Smaller bandwidths usually generalize better on these toy sets (see Shaydulin and Wild, "Importance of kernel bandwidth in quantum machine learning", Phys. Rev. A 106, 042407, 2022).
    • A classical RBF SVM baseline is always reported unless classical_baseline=false. On these toy datasets the RBF baseline is often as good or better. Nothing here is evidence of quantum advantage.

    Notes on qaoa_maxcut¶

    • edges is [[u, v], ...] or [[u, v, weight], ...], nodes 0..n-1.
    • Circuit: Hadamards, then per layer cx, rz(2*gamma*w), cx for every edge and rx(2*beta) mixers, executed through the SuperQuantX unified backend API. Parameters come from a coarse grid search refined with COBYLA (scipy).
    • The result includes the exact brute-force optimum, the approximation ratio (expected cut divided by max cut), the probability of sampling an optimal cut, and found_optimum.

    Limits and safety¶

    Inputs are validated and capped. Defaults can be lowered or raised with environment variables, but never above the hard ceiling:

    Variable Default Hard ceiling
    SUPERQUANTX_MCP_MAX_QUBITS 10 16
    SUPERQUANTX_MCP_MAX_SHOTS 10000 100000
    SUPERQUANTX_MCP_MAX_GATES 500 2000
    SUPERQUANTX_MCP_MAX_QASM_CHARS 20000 50000
    SUPERQUANTX_MCP_MAX_SAMPLES 80 200
    SUPERQUANTX_MCP_MAX_FEATURES 4 6
    SUPERQUANTX_MCP_MAX_QAOA_NODES 10 12
    SUPERQUANTX_MCP_MAX_QAOA_LAYERS 3 4

    Hardware is off by default. Tools only use local simulators (simulator, Qiskit Aer, PennyLane default.qubit, and the default local devices of the other SDKs). Passing a device to run_circuit is refused unless the server was started with SUPERQUANTX_MCP_ALLOW_HARDWARE=1, and even then the backend SDK's own credentials and configuration are required. Annealing-only backends (D-Wave Ocean) are listed but not used for gate circuits.

    All tools are annotated read-only and do not touch the filesystem. Logs go to stderr so they never corrupt the stdio protocol stream.

    Client configuration¶

    Use the absolute path of the superquantx-mcp script from the environment where you installed SuperQuantX (which superquantx-mcp).

    Claude Desktop¶

    Edit claude_desktop_config.json (macOS: ~/Library/Application Support/Claude/, Windows: %APPDATA%\Claude\):

    {
  "mcpServers": {
    "superquantx": {
      "command": "/absolute/path/to/venv/bin/superquantx-mcp",
      "args": [],
      "env": {
        "SUPERQUANTX_MCP_MAX_QUBITS": "10"
      }
    }
  }
}

    Cursor¶

    Create .cursor/mcp.json in your project (or ~/.cursor/mcp.json for all projects):

    {
  "mcpServers": {
    "superquantx": {
      "command": "/absolute/path/to/venv/bin/python",
      "args": ["-m", "superquantx.mcp"]
    }
  }
}

    Without a pre-made virtualenv (uvx)¶

    Since 0.3.0, uvx can run the server in an isolated environment:

    {
  "mcpServers": {
    "superquantx": {
      "command": "uvx",
      "args": ["--from", "superquantx[mcp,qiskit,pennylane]==0.3.0", "superquantx-mcp"]
    }
  }
}

    Use SuperQuantX 0.3.0 or newer; 0.2.0 does not include the MCP server.

    Programmatic client¶

    examples/mcp_client_demo.py launches the server over stdio with the official SDK client and calls every tool:

    Requires a running MCP client session

    Illustrates the official MCP Python client; skipped in the docs checker because it launches a subprocess server.

    import asyncio
from mcp import ClientSession, StdioServerParameters
from mcp.client.stdio import stdio_client

params = StdioServerParameters(command="python", args=["-m", "superquantx.mcp"])

async def main():
    async with stdio_client(params) as (read, write):
        async with ClientSession(read, write) as client:
            await client.initialize()
            result = await client.call_tool("bell_state_demo", {"shots": 1000})
            print(result)

asyncio.run(main())

    How it relates to the IBM Qiskit MCP servers¶

    IBM maintains Qiskit MCP servers for the Qiskit stack (Qiskit, Qiskit IBM Runtime, the IBM transpiler service, and Qiskit Code Assistant). Those are the right choice for deep IBM Quantum workflows such as managing Runtime jobs on IBM hardware.

    The SuperQuantX server is complementary: it is multi-backend. One circuit, one call, and the assistant can compare the built-in simulator, Qiskit Aer, PennyLane, and (when installed) Cirq, Braket, and TKET backends, plus ready-made QML and optimization experiments with classical baselines. You can enable both servers in the same client.

    Known limitations¶

    • Everything runs on noiseless local simulators at toy scale (at most 16 qubits). Results show the workflow, not a quantum advantage.
    • Tested backends: built-in simulator, Qiskit Aer, PennyLane default.qubit. Cirq, Braket, and TKET go through the same unified backend code path but were not installed in the verification run.
    • The MCP QAOA tool has its own grid-search and COBYLA parameter search on top of the unified circuit API. The library's QAOA.solve also runs real circuits and reports a classical optimum. The MCP statevector QSVM mode retains its explicit Qiskit-convention encoding; backend mode uses the shared library feature maps, so the two modes can produce different valid kernels.
